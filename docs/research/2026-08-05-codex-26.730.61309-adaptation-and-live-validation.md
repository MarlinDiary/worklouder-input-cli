## Provider recovery result

A new Codex service can report `detected`, or even `connected`, before it is
usable. The adapter therefore distinguishes structural connection from verified
ownership. Codex acquisition now requires:

- lifecycle `started`;
- comm and API present;
- HID and joystick subscriptions present;
- one successful bounded RPC probe.

The 26.730.61309 service could block in startup lighting/battery work while an
older native request was being released. Recovery performs a bounded stop,
forces the prior comm disconnect when necessary, temporarily bypasses only the
startup lighting/battery calls, restores the original official methods, and
then requires subscriptions plus the RPC probe.

Observed successful receipt:

```json
{
  "provider": "codex",
  "startupRpcBypassed": true,
  "rpcProbe": {"succeeded": true, "operation": "getFileList", "fileCount": 0},
  "state": {
    "lifecycleState": "started",
    "deviceState": {"status": "connected", "transport": "bluetooth"},
    "rpcVerified": true,
    "hasComm": true,
    "hasApi": true,
    "hasHidSubscription": true,
    "hasJoystickSubscription": true
  }
}
```

A repeated final `provider status` returned Codex in that state and Input not
running. No GUI was activated or navigated.

The first draft of `codex runtime status` still used the earlier one-shot Node
inspector path. Repeated attachment exposed a release-specific failure: after
the one-shot handler had been consumed, another `SIGUSR1` could terminate the
Codex main process instead of opening port 9229. The runtime commands now use
the persistent authenticated Codex bridge and advertise
`codex.runtime.status.v1` plus `codex.runtime.recover.v1`. The exact-release
installer publishes a revisioned ESM module root, and the embedded
provider runtime is content addressed so an older Electron module cache cannot
win after an in-place CLI update.

Live recovery began from `deviceState.status=error` with
`error=connection-failed` and completed in the same Codex PID with
`deviceState.status=connected`, comm/API present, both subscriptions present,
and no pending connect/topology Promise. Three subsequent one-second-spaced
status reads were all `healthy=true` and `inspectorOpenedByCli=false`.

## Corrected device-configuration authority

The Codex-bundled OAI API accepted the connection and input subscriptions, but
on this Bluetooth session its generic file list was empty, reads of
`keymap.json` returned no bytes, and `device.status` timed out. Treating that
session as a complete configuration writer would therefore be incorrect.
Input 0.18.0 and its bundled device kit remain the byte authority.

`device status/files/export` and `device config snapshot/validate/apply/restore`
now use this sequence for `--owner auto` or `--owner codex`:

1. record the healthy current owner;
2. serialize provider and device operations;
3. acquire a hidden Input session;
4. require a real Input `device.status` RPC response;
5. perform the guarded Input bridge operation;
6. restore Codex and require subscriptions plus its RPC probe;
7. restore Codex on any Input acquisition or operation failure.

Input connection counters alone no longer establish readiness. A live stale
Input handle reproduced `Request timed out`; the command stopped before a
configuration write, quiesced Input, and restored the verified Codex owner. The
pre-existing device baseline revision remained
`4be123af519b02a801819b2ad4de38f3f78f84ee97b7d0a9ee76669a33c22028`.

A later explicit retry reproduced the same Input RPC timeout. Its automatic
rollback reacquired Codex, completed `getFileList`, set `rpcVerified=true`, and
restored comm/API plus both subscriptions. This proves the new lease rollback
path but also confirms that a fresh 0.1.1 device mutation still requires a
working Input RPC session, typically the device's USB configuration transport,
before the first byte can be written.

This run verifies fail-closed automatic-update behavior, exact-release schema
adaptation, Codex subscribed recovery, RPC-health-gated ownership, and rollback
to Codex after an unhealthy Input lease. A fresh Input apply/readback/restore
record for this exact Codex update must show a successful Input RPC probe before
it can extend the earlier device-mutation evidence.
